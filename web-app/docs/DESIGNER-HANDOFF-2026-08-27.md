## 1. 先做這件事:打開 demo panel,自己把七個狀態切出來看

1. 開發端啟動後(`npm run dev`),在任何網址後面加 **`?demo=1`**,例如
   <http://localhost:3000/history?demo=1>
2. 左下角會出現一顆 **`DEMO`** 小把手,點一下展開
3. 面板上有 **8 個開關**,每一個對應下面 §2 的一個情境。切下去,畫面就會進入那個狀態

**面板上寫著「⧗ awaiting designer artwork」的開關,就是在等你的稿。** 那表示狀態已經接好、
可以觸發,但畫面本體還沒有東西可畫 —— 所以你切下去可能會看到一片空白,**那就是現況,不是壞掉**。

面板預設是隱藏的(只有加了 `?demo=1` 才出現),所以它不會出現在任何截圖或正式 demo 裡。
按 `[x]` 可以永久關掉,要叫回來就再加一次 `?demo=1`。

## 2. 要畫的 15 張

### 2.1 History 無紀錄 —— **4 張**

- **開關:** `History — no records`
- **看得到的網址:** <http://localhost:3000/history?demo=1>
- **四個 tab 各要一張:** `All` · `Music Videos` · `Songs` · `Liked`
- **現況:** 一段通用文字,四個 tab 共用,只換名詞(「Nothing here yet. Your creations will
  appear here.」)
- **為什麼四張不能共用一張:** `Liked` 的語意跟其他三個不一樣 —— 它是「你在社群上按過愛心的
  別人的作品」,不是你自己的創作。所以它空的時候該說的話跟「你還沒有創作」完全不同,而且它在
  真實使用中**空的機率比其他三個高很多**。

### 2.2 Create MV → Choose Song → My Songs 空 —— **1 張(但先看現況再決定要不要畫)**

- **開關:** `Create MV → Choose Song — My Songs empty`
- **看得到的網址:** <http://localhost:3000/mv/room?demo=1> → 點 Choose Song → `My Songs` tab
- **現況:** ⚠️ **七項裡唯一已經有 UI 的。** 我們自撰了一版(用 DP 自己的
  `.mv-settings__row-title` / `--desc` 排版 + 共用 `.button` 元件),因為 DP 的歌曲目錄是常數、
  永遠不可能空,所以 DP 沒有這張稿。
- **所以這一項的問題是「要不要換掉」,不是「畫一張」。** 請先打開來看,再決定。
- 補充:新使用者的 My Songs **本來就是空的**,這是預設狀態,不是邊緣情況。

### 2.3 Credits Detail 無紀錄 —— **3 張**

- **開關:** `Credits Detail — no records`
- **看得到的網址:** <http://localhost:3000/profile/credits?demo=1>
- **三個 tab 各要一張:** `All` · `Spend` · `Earn`
- **現況:** 🔴 **一片空白。** 程式碼直接展開清單,零筆就什麼都不畫 —— 連空狀態的容器都沒有。
- **為什麼三張:** `Spend` / `Earn` 是依金額正負推導的,所以「有 Earn 但沒有 Spend」是很常見的
  真實情況(剛註冊、拿了贈點、還沒花過)。只畫「全部都空」會漏掉最常發生的那一種。

### 2.4 Community profile 無作品 —— **3 張**

- **開關:** `Community profile — no MVs / Songs`
- **看得到的網址:**
  - 自己的公開頁:<http://localhost:3000/creator?self=1&demo=1>
  - 別人的頁:<http://localhost:3000/creator?demo=1>
  - 自己的帳號頁:<http://localhost:3000/profile?demo=1>(Music Videos / Songs 兩個 tab)
- **現況:** 🔴 **兩個畫面都一片空白。**
- **🔴 這三張最重要的一件事:自己的和別人的不能共用。**
  - **自己的**空頁 → **要有一顆「去建立」的 CTA**
  - **別人的**空頁 → **不能有 CTA**。叫使用者去幫別人建立作品在邏輯上是錯的
  - 程式上這兩種視角是靠網址的 `?self=1` 區分的,所以兩張稿都畫得出來、也都會被用到

### 2.5 送審被 reject —— **2 處 UI**,共用 7 種原因文案

- **開關:** `Publish review REJECTED`(打開後面板會多一個下拉,可以切換 7 種原因)
- **看得到的網址:** <http://localhost:3000/history?demo=1> 與
  <http://localhost:3000/mv/result?demo=1>
- **要畫的兩處(產品負責人指定,不是四處):**
  1. **History 列表的卡片上。** 目前卡面上**完全看不出審核狀態** —— 只有 ⋯ 菜單裡有一列
     「Publish (Review)」配一個沙漏 icon。所以這裡需要的是**卡片本身**的一個狀態表現。
  2. **`/mv/result` 的 Publish 區塊。** 這裡已經有一行狀態文字(`Published · pending review`
     / `Off`),reject 是第三種。
- **明確不畫:** Community / Creator profile(被 reject 的內容本來就不該出現在公開頁,那裡是
  「消失」而不是「顯示 reject」)、以及歌曲的結果頁(見下)。
- **7 種原因的文案已經定稿,請照這個字面用:**

  | 順序 | 文案                         |
  | ---- | ---------------------------- |
  | 1    | Platform Policy Violation    |
  | 2    | Explicit / Adult Content     |
  | 3    | Violence or Disturbing       |
  | 4    | Hate Speech / Discrimination |
  | 5    | Suspected Copyright Issue    |
  | 6    | Poor Audio / Video Quality   |
  | 7    | Duplicate Content            |

- **兩個已經拍板、不用再問的規則:**
  1. **被 reject 後會自動回到「未發布」,使用者可以編輯、可以重新送審。** 所以這個 UI 需要一條
     出路,不是死巷。
  2. **只有 MV 送審,歌曲直接上架。** 所以歌曲不會有 reject 畫面 —— 即使 7 種原因裡的
     「音訊品質不佳」和「版權疑慮」對歌曲才最適用。**這是拍板的產品決定,不是漏掉。**

### 2.6 後端 API 錯誤 —— **1 張整頁**

- **開關:** `Backend API error`
- **現況:** 🔴 全站**沒有任何錯誤頁**。
- **要畫的是「整頁級」的錯誤** —— 頁面根本載不起來的那種。要有一顆 Retry。
- **不要畫的是** flow 進行中的生成失敗:那個已經有 inline 的錯誤 + Retry UI 了
  (可以用面板的 `Generation job fails` 開關看到現況)。兩種失敗本質不同,不要統一。

### 2.7 手機訂閱者想在網頁取消訂閱 —— **1 張 dialog**

- **開關:** `Subscribed on a phone (App Store / Google Play)`(打開後面板會多一個下拉,可以切
  iOS / Android)
- **看得到的網址:** <http://localhost:3000/settings?demo=1> → 點 **Unsubscribe** 那一列
- **情境:** 使用者在手機 app 裡訂閱(綁在 App Store 或 Google Play,不是 YCM 官網帳號),
  之後想在電腦上取消。網頁**做不到**,必須引導他回手機的商店設定取消。
- **現況:** `/settings` 已經有 **Unsubscribe** 這一列,點了會開一個「Unsubscribe?」確認框。
  你要畫的是**取代那個確認框**的提示 dialog —— 但只在「他是在手機訂的」時候。
- **要涵蓋兩種平台:** App Store(iOS)與 Google Play(Android)的路徑指示不一樣,請確認稿上
  的步驟文字是否要分兩版。
- 補充:如果使用者是**在網頁上訂閱**的,那走的是現有的取消流程,不是這張 dialog。

## 3. 畫的時候要遵守的既有規則(這些不是建議,是程式上會出事的)

### 3.1 六個寬度

**320 / 375 / 768 / 1024 / 1440 / 1920**。320 是最低支援寬度。
768 是「手機 / 桌機」的分界(手機以下換成 MobileHeader + MobileTabBar)。

**最容易漏的是 320 和 375。** 已知 DP 有幾處在這兩個寬度出問題(例如
`TopSongListItem.css` 一條 media query 都沒有,320px 的歌名被截到剩 1–2 個字 —— 見
`DESIGNER-TODO` A8)。空狀態通常是一個置中的區塊,在窄寬度反而比較安全,但**請至少確認 320**。

### 3.2 顏色一定要走 token,不要自己挑

顏色來源是 `designer-prototype/src/styles/tokens.css`(我們是整份同步過來的,不逐個改值)。

⚠️ **這一點有前科,而且是同一個系統性成因:** `DESIGNER-TODO` 的 **A1 / A9 / A13** 都是
「對比度不到 WCAG AA」的既有缺陷 —— A9 是 MobileTabBar 未選中文字 **3.74:1**,A13 是 Account 頁
的 stats 說明文字約 **3.3–3.8:1**。空狀態畫面的特徵正是「大量次要色的說明文字」,**是最容易再
撞上這個問題的一類畫面**。次要文字請確保 **≥ 4.5:1**(大字 ≥ 3:1)。

### 3.3 觸控目標 ≥ 24×24

`DESIGNER-TODO` A10 記了 6 個手機上小於 24×24 的控制項(WCAG 2.5.8 AA)。空狀態裡的 CTA 按鈕
請不要再增加一個。

### 3.4 能用既有元件就用既有元件

`src/styles/designer/` 底下有 46 支從 DP 逐字複製過來的 stylesheet,包含共用的
`Button.css` / `Badge.css` / `Card.css` / `Chip.css`。**空狀態的 CTA 請用既有的 `Button`
variant,不要新畫一種按鈕** —— 每多一種新樣式,就多一份要維護的 CSS,而空狀態不值得。

### ⚠️ 交稿時最容易出事的兩件事(都真的發生過)

1. **`src/assets/hero/` 這個資料夾一定要一起進 repo。** 程式碼是**逐個檔名 import** 它的 ——
   少一個檔案,整個 module graph 就掛掉,**每一條路由都會變成白畫面**。這個症狀曾經被誤判成
   「某一頁壞了」誤讀了四次交接(`DESIGNER-TODO` A12)。
2. **如果這次交稿順手修了既有的畫面,請說一聲。** 我們這邊有一份 `designer-overrides.css`,
   裡面每一條都是在補一個當時的稿面缺陷。新的一版可能已經把那個缺陷修掉了 ——
   這時候**我們的 override 就變成新的 bug**。drop 2 就發生過:兩邊的修正互相抵銷,
   `/explore/songs` 在手機上變成一條既沒有 tab 也沒有返回鍵的空白 bar,而所有自動化檢查
   **全部是綠的**。所以請把「這次改了哪些既有畫面」列出來,不要只交新增的。
