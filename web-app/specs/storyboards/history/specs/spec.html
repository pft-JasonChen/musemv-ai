History (My Creations)

Draft ·Version: v1 · Author: Jason Chen · Date: 2026-08-27 ·Guideline: Open ↗

The signed-in user’s “My Creations” list (/history): filterable cards merging live in-memory jobs with a static seed, a per-row ⋯ options menu, and the delete/publish confirm flows.

Background
The third spec in this repo’s yco-spec storyboard programme (specs/storyboards/PLAN.md), following the trial Song Creation spec (S1) and preceding the shared Credits IAP spec (S5). Both S1 and S2 (AI Music Video) already end their happy paths with one step showing the new row appear in History and explicitly leave History’s own behavior out of scope — this spec is what pays that off.
Goal
Give QA a screenshot-led walkthrough of every /history behavior they can follow without cross-referencing code.
Reading this spec. This is a behavior specification for the front-end RD, not production code — the prototype source cannot be reused. Each step card shows the screenshot first, then what the user does (bold) and what the WEB UI shows, with on-screen text, rules & limits, and input/output below. On a screenshot, a solid red frame marks the click that advances the flow; a dashed amber frame marks a key point to note (hover a frame for its label). Steps carry a stable ID (e.g. P1-S2).
PlatformYouCam Muse Web (desktop) — captured at 1440px
AudienceQA
ScopeBrowse & filter, opening a creation, the ⋯ menu (all five row-type variants), Publish, Delete, and the Edit MV / Create MV menu actions (tap only — see P6).
Out of scopeThe destination screens themselves (/mv/result area 02, /song/result area 03, /mv/storyboard & /mv/edit area 02, /song/play area 04) — each gets one arrival step here and no further tour.

⚠ Prototype Simplifications — NOT the production contract

Where the prototype fakes or stubs behaviour. Build the production must do column — never the prototype behaviour.

AreaPrototype doesProduction must do
Live rows are in-memory onlyLive jobs prepended to the list vanish on a full page reload; only the static 8-row seed remains, and every override (liked/published/removed) resets with it.A real history endpoint (TBD-HIST-01, TBD-GL-04) must persist rows and their state server-side across reloads and devices.
Like / Publish / Delete are all local overridesNone of the three write anywhere — `liked`/`published`/`reviewing` live in a per-row `ov` map in component state, and Delete just adds the id to a `removed` set. No API call is made for any of them.Real endpoints must exist for each; Publish additionally needs the moderation/review pipeline into the community feed that decides reviewing → published or reviewing → rejected (TBD-HIST-04, and the rejected half is TBD-HIST-05).
Download uses fixture media, not the row’s own renderEvery song download is the same shared sample audio file; every mv/storyboard download is the same shared sample video file, regardless of which row triggered it.A real render pipeline must serve each row’s own generated file at download time.
