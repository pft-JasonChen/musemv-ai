Shell & Auth

Draft ·Version: v1 · Author: Jason Chen · Date: 2026-08-27 ·Guideline: Open ↗

The persistent app frame — sidebar / bottom tab bar, each route’s own inline account cluster, and the mock sign-in gate (SignInModal / AuthGuard) that every other area assumes is already in place.

Background
The sixth spec in this repo’s yco-spec storyboard programme (specs/storyboards/PLAN.md), covering areas 01 (App Shell) and 09 (Auth & Onboarding) as one spec (D4) because SHELL-P2 (gated nav while logged out) IS AUTH-P2’s trigger — splitting them would put the trigger and the response in different documents.
Goal
Give QA a screenshot-led walkthrough of every shell/auth behavior they can follow without cross-referencing code.
Reading this spec. This is a behavior specification for the front-end RD, not production code — the prototype source cannot be reused. Each step card shows the screenshot first, then what the user does (bold) and what the WEB UI shows, with on-screen text, rules & limits, and input/output below. On a screenshot, a solid red frame marks the click that advances the flow; a dashed amber frame marks a key point to note (hover a frame for its label). Steps carry a stable ID (e.g. P1-S2).
PlatformYouCam Muse Web — captured at 1403×697 (desktop) AND 375×812 (phone), the one exception in this programme (D8)
AudienceQA
ScopeSigned-in navigation, gated nav vs. gated route entry, header Sign In, account entry points (there is no account menu — see the Feature block), sign-out + reload behavior, and the bare /share page.
Out of scopeBuyCreditsModal/SubscribeModal’s own content (area 07 / S5), /profile itself (area 06 / S7), /history itself (area 05 / S4), /share’s own content (S9) — each gets one arrival step here and no further tour.
